# AGENTS.md — правила работы агентов в проекте GPN Restyler

## 0. Состав проекта

- Корень проекта: `/Users/wysockii/Documents/gpn_slides`
- Код: `gpn-restyler`, ветка `gpn-restyler` (nested-clone layout).
- Корпуса (`ontology/`, `slide_examples/`) — только чтение, никогда не менять.
- Статус разработки: `development_history.md` (история по этапам).
- Техническое состояние: `gpn-restyler/IMPLEMENTATION_STATE.md`.

## 1. ГЛАВНОЕ ПРАВИЛО: статус дополняется, а не переписывается

После каждого этапа разработки агент ОБЯЗАН дописать новый раздел
в `development_history.md`.

- **НО ОБЯЗАТЕЛЬНО БЕЗ УДАЛЕНИЯ ПРЕДЫДУЩЕГО СТАТУСА.**
  Старые разделы (Этапы 0, 1, 2, 3, …) — неприкосновенны:
  их нельзя удалять, сокращать, сливать или переформулировать.
- Каждый новый раздел пишется ПОСЛЕ всех предыдущих, в том же формате:
  `Реализовано / Проблемы / Тесты / Запросы пользователя / Предстоит`.
- Если на новом этапе выяснилось, что старый статус был неточен,
  правда фиксируется в НОВОМ разделе (пункт «Проблемы» или «Уточнение
  к Этапу N»), а старый текст остаётся как есть — история должна показывать,
  что знали на тот момент.
- То же правило действует для `IMPLEMENTATION_STATE.md`:
  новые факты добавляются, старые строки не удаляются без явного
  требования пользователя.

## 2. Проверяемость вместо намерений

- Каждый claim статуса подтверждается командой/артефактом/тестом
  (путь, exit-код, хэш). Незапущенное не приписывать себе.
- Прогоны пишутся в НОВЫЙ `runs/<stage>/<run_id>/`, старые не перезаписывать.
- Хэши корпусов сверяются до и после работ.

## 3. Запреты по умолчанию

- Не делать `reset` / `rebase` / `force push`; чужие changes сохранять.
- Не скачивать корпоративные шрифты; `needs_assets` — честный статус, а не сбой.
- Не стартовать следующий этап автоматически; следующий шаг — только запись
  в пункте «Предстоит».
